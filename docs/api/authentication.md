# Ratib API authentication

Ratib API service accounts are organization-scoped machine identities. Creating one registers
a P-256 public key. The private key is generated by and remains with the customer. A service
account is not a Privy signer and cannot approve an intent or change wallet authority.

## Required headers

Every `/v1` request includes:

- `X-Ratib-Key-Id`: the registered credential ID.
- `X-Ratib-Timestamp`: the current Unix time in milliseconds. Ratib accepts five minutes of skew.
- `X-Ratib-Nonce`: a unique 16-120 character base64url value. Reuse is rejected.
- `X-Ratib-Content-SHA256`: base64url SHA-256 of the exact body, or the empty string for GET.
- `X-Ratib-Signature`: an ES256 signature encoded as base64url.
- `Idempotency-Key`: required for side-effecting requests.

Build the signed message with these exact newline-separated fields:

```text
method:POST
target:/v1/payments
content-digest:<base64url sha256>
timestamp:<unix milliseconds>
nonce:<unique base64url nonce>
credential:<rcred_...>
idempotency-key:<key or empty string>
```

The target is the exact path and query string sent over HTTP. The signature covers the body
digest and idempotency key, so neither can be changed after signing.

## TypeScript example

```ts
import { createHash, createPrivateKey, randomBytes, sign } from 'node:crypto';

const body = JSON.stringify({
	walletId: process.env.RATIB_WALLET_ID,
	asset: 'USDC',
	amount: '25.00',
	destination: '0x0000000000000000000000000000000000000001',
	reference: 'INV-2026-1042'
});
const path = '/v1/payments';
const timestamp = String(Date.now());
const nonce = randomBytes(24).toString('base64url');
const idempotencyKey = crypto.randomUUID();
const digest = createHash('sha256').update(body).digest('base64url');
const message = [
	'method:POST',
	`target:${path}`,
	`content-digest:${digest}`,
	`timestamp:${timestamp}`,
	`nonce:${nonce}`,
	`credential:${process.env.RATIB_KEY_ID}`,
	`idempotency-key:${idempotencyKey}`
].join('\n');
const signature = sign('sha256', Buffer.from(message), {
	key: createPrivateKey({ key: JSON.parse(process.env.RATIB_PRIVATE_JWK!), format: 'jwk' }),
	dsaEncoding: 'ieee-p1363'
}).toString('base64url');

const response = await fetch(`${process.env.RATIB_API_URL}${path}`, {
	method: 'POST',
	body,
	headers: {
		'content-type': 'application/json',
		'x-ratib-key-id': process.env.RATIB_KEY_ID!,
		'x-ratib-timestamp': timestamp,
		'x-ratib-nonce': nonce,
		'x-ratib-content-sha256': digest,
		'x-ratib-signature': signature,
		'idempotency-key': idempotencyKey
	}
});
```

Request signatures use the 64-byte IEEE P1363 encoding (`r || s`), matching Web Crypto ES256.

## Short-lived access tokens

For clients that prefer bearer authentication, send a signed `POST /v1/auth/token` request.
Ratib returns a ten-minute `access_token`. Bearer requests still require the current timestamp,
fresh `X-Ratib-Nonce`, content digest, and ES256 signature; writes additionally require
`Idempotency-Key`. Credential revocation, account
expiry, organization status, current scopes, and wallet restrictions are checked on every call.
Tokens are only an API transport credential and never grant Privy signing or approval authority.

## Retry behavior

Reuse the original `Idempotency-Key` and exact body after a timeout. Use a new nonce, timestamp,
and signature for each HTTP attempt. An identical request returns the original operation. Reusing
the key with a different body returns `409 idempotency_key_reused`. An ambiguous Privy result is
reconciled by Ratib using the operation correlation ID before any provider-side retry.

## Webhook verification

Ratib signs `{event-id}.{timestamp}.{raw-body}` with its platform ES256 key using ASN.1 DER
signature encoding. Read the public key
from `/v1/.well-known/webhook-jwks.json`, select the `kid` in `X-Ratib-Signature`, verify against
the untouched body, reject stale timestamps, and deduplicate on `X-Ratib-Event-Id`. Delivery is
at least once and only ordered within an aggregate through `aggregate.sequence`.
